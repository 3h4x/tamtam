# API Routes

Complete reference for TamTam HTTP API routes. All routes live under `app/api/`. New routes must have a matching test in `__tests__/api/<route-name>.test.ts`.

When `auth_token` is configured in Settings, middleware requires either `Authorization: Bearer <token>` or the httpOnly `tamtam_auth` cookie for every API route except `/api/health` and `/api/auth/*`. Without `auth_token`, TamTam remains in localhost-only dev mode.

## Auth

- `/login` — Browser login form. Posts the shared token to `/api/auth/login`, which sets the httpOnly cookie used by the UI and SSE/EventSource requests.
- `/api/auth/check` — Middleware/session check (GET). Returns `{ ok: true, configured: false }` when auth is disabled, `{ ok: true, configured: true }` for a valid bearer/cookie token, or `401` otherwise.
- `/api/auth/login` — Cookie login (POST: `{ token }`). Verifies the shared token against the stored `auth_token` hash and sets `tamtam_auth`.
- `/api/auth/logout` — Clears the `tamtam_auth` cookie (POST).

## Agents

- `/api/agents` — CRUD for agents (GET: accepts `?project=` and `?name=` filters, plus `?fields=summary` for list views that need only id/name/project/schedule/enabled/model/provider/source/kind plus live schedule telemetry; POST). GET annotates each returned agent with `cron` (`nextFireMs`, `attempts`, `isAvailable`, `lockedAt`, `lastError`) when a graphile-worker `agent-cron-<id>` row exists, and `lastAttempt` (`at`, `status`, `reason`) when the in-process cron worker has recently skipped, queued, or dispatched that agent. Agent names are trimmed, must be non-empty, and may not contain slashes, backslashes, or control characters. Project-local uniqueness is case-insensitive, so case-only duplicates are rejected across DB-backed agents with `409 { detail }`; system-agent seeding uses the same conflict rule and skips instead of shadowing an existing user agent. It accepts optional `docPaths` (project-relative docs attached to the agent context), `provider` (required CLI provider when set; `null` means "any enabled provider"), and `prerequisiteCommand`, a shell command stored on the agent and run before the agent CLI starts. When `skillIds` contains `agent-issue-cruncher` and `prerequisiteCommand` is omitted, TamTam stores a default `pick_top` issue fetch against the local API; explicit `null` / empty-string clears remain cleared instead of re-enabling that default. `POST` creates only `kind: "user"` rows; `kind: "system"` is reserved for TamTam's built-in seeder and returns `400`.
- `/api/agents/[agentId]` — Agent detail (GET, PATCH, DELETE). PATCH accepts optional `docPaths`, `provider`, `prerequisiteCommand`, and audit `note`; `null` or an empty string clears `provider`/`prerequisiteCommand`. Every DB-backed PATCH writes the previous row to `agent_revisions` before applying the update. Name updates follow the same validation and case-insensitive per-project duplicate checks as create and return `409 { detail }` on conflict. For `kind: "system"` rows, PATCH accepts only `enabled`; `schedule` returns `400 { detail }`, and identity/behavior fields are ignored because the handler owns them. DELETE of a system agent records a dismissal marker in `settings` before removing the row.
- `/api/agents/[agentId]/revisions` — Agent revision history (GET). Returns `{ revisions }` newest-first, each with the raw JSON `snapshot`, parsed `parsedSnapshot`, `author`, optional `note`, and `createdAt`.
- `/api/agents/[agentId]/revert` — Revert a DB-backed agent to a prior revision (POST: `{ revisionId }`). The current row is first recorded as a new revision, then the snapshot is restored, agents cache is cleared, and the schedule is reinstalled/uninstalled as needed.
- `/api/agents/[agentId]/run` — Run agent (POST) — body accepts `{ prompt: string, readOnly?: boolean, model?: 'fast'|'normal'|'smart'|'haiku'|'sonnet'|'opus' }`. `model` is an optional per-run override used by orchestrator boost fires; invalid non-empty model values return `400 { detail: 'Invalid model...' }` instead of falling back silently. For user agents, the route pre-estimates selected skills, attached docs, task prompt, base prompt, and project memory before creating a job; oversized runs return `413 { code: 'prompt_estimate_blocked', detail, prompt_estimate }` before any job row or provider process exists. Accepted user-agent starts return `200 { status: 'started', job_id, pid: 0, agent, via: 'workflow', prompt_estimate }`, then hand off to the durable workflow intake which composes skills + attached docs, runs the optional `prerequisiteCommand` with `bash -c` in the project directory (output captured to `<logDir>/<jobId>.prereq.txt` and prepended to the agent prompt), injects retrieval/memory, and spawns the agent CLI as a detached child process. Agents with `fallbackEnabled` may retry once on the next provider in `provider_fallback_chain` when the first CLI exits non-zero with transient output; the retry transition is appended to the run log. `pid` is `0` because the route returns before the workflow has spawned the child; poll `/api/jobs/<job_id>` to get the real PID. For system agents, the same route runs the registered internal handler immediately, does not require `prompt`, does not start CLI intake, and returns `200 { status: 'started', job_id, pid: 0, agent, via: 'system' }`. Returns `500 { detail }` when the workflow runtime fails to enqueue (for example, the configured workflow world cannot start or its backing store is unavailable). TamTam defaults to the local workflow world (`WORKFLOW_TARGET_WORLD=local`, `WORKFLOW_LOCAL_DATA_DIR=data/workflow-data`), while operators may override the workflow world explicitly. Returns `202 { status: 'queued', detail, agent, blockingJobId?, code? }` when another agent on the same project is running/still starting, when an active release lock defers the run with `code: 'pipeline_lock'`, or when an older queued release must run first with `code: 'pending_release'`; deferred runs preserve any validated per-run model override through both the in-memory agent queue and the DB-backed release-lock queue. Returns `409 { code: 'already_running'|'already_starting'|'project_busy'|'project_paused'|'system_agent_handler_missing', detail, blockingJobId? }` for same-agent duplicates, start-slot duplicates, when a non-agent project job is already running, when the project has its per-project pause toggle set, or when a system row has no handler. Returns `429 { code: 'budget_exceeded', detail, agent }` when the project's rolling 24h spend has reached `daily_spend_cap_usd`; TamTam records a blocked agent job and emits `budget_exceeded` when that notification is enabled. With `readOnly: true`, the route skips local-worktree serialization gates for user agents: non-agent project busy checks, different-agent queueing/start-slot checks, pending-release re-acquire checks, and dirty-worktree checks. It still enforces same-agent duplicate rejection, active release pipeline locks, project spend caps, and CLI quota/pause gates. Agent names and skill IDs do not affect this bypass. Manual agent runs are allowed on `fix/issue-*` branches; scheduled runs are still skipped there by the internal scheduler. Manual (non-scheduled) agent runs bypass `jobs_paused`; scheduled runs are still blocked by the global pause.
- `/api/agents/by-name` — Update agent by project+name without knowing its UUID. PATCH accepts `{ project, name, ...fields }` for in-place updates where `name` is the lookup key, or `{ project, currentName, name, ...fields }` when the caller needs to rename the agent while selecting it by the old name. It mirrors `/api/agents/[agentId]` writable fields and system-agent restrictions, including `docPaths`, `provider`, `prerequisiteCommand`, and audit `note`, and enables agents to self-improve. Updates write `agent_revisions` before mutation. Lookup and rename names use the same validation rules as create/update, and renames run the same case-insensitive per-project conflict checks before a write.
- `/api/agents/stats` — Per-agent aggregates for an Overview dashboard. GET requires `?project=<name>` and returns `200 { project, agents: [{ name, runs, finishedRuns, successfulRuns, avgDurationMs, totalDurationMs, inputTokens, outputTokens, cacheReadTokens, cacheCreateTokens, costUsd, modifiedFilesCount, reviewFixesTriggered }] }`; returns `400` when `project` is missing and `500 { detail }` on unexpected database errors. Aggregates are computed from rows in `jobs` whose `kind = 'agent:<name>'`. `reviewFixesTriggered` counts `fix` jobs that share a `release_id` with one of this agent's runs and is non-zero only when the agent name matches `/review/i` — a rough proxy for "fixes triggered per review".
- `/api/agents/improve-prompt` — Rewrite a draft agent prompt with project context (POST: `{ project, draftPrompt, skillIds?, docPaths?, agentId?, agentName? }`). The route builds context from TamTam's agent primer, project `CLAUDE.md`, selected docs, and selected skills/personas, then invokes the configured Claude-compatible fast provider. When `agentId`/`agentName` identify an existing agent, the route also folds in that agent's recent run outcomes (`lib/agents/run-feedback.ts`) — but only when the agent has a low-yield pattern — so the rewrite can target *why* recent runs produced nothing rather than just polishing prose. Returns `200 { improvedPrompt }`; returns `400` for invalid input, `404` when the project is unknown, `413` when `draftPrompt` exceeds 32 KiB, `429 { code: 'providers_over_budget', detail }` when all enabled providers are budget-blocked, and `502` when the provider exits unsuccessfully or returns empty output. No job row is created.
- `/api/agents/scheduler-health` — Verify enabled scheduled agents have both their persisted prompt file and a graphile-worker `agent-cron-<id>` queue row (GET returns `{ ok, expected, actual: { graphile }, missing, orphans: { graphile }, errors, internal: { started, entries: [...] } }`; `missing[]` entries include `promptFileLoaded` and `queueLoaded`). POST reinstalls anything missing, returns `{ before, after, installed, installFailures }`. Surfaced on `/monitoring`.
- `/api/agent-catalog` — Built-in agent catalog (GET). Returns `{ entries }`, where each entry includes public template metadata (`name`, `aliases`, `description`, `dispatch`, `defaultSchedule`, `defaultModel`, `prompt`, `skillIds`, `autoSeed`, `tier`, `fallbackEnabled`, `inspiration`, `requires`, `outputs`, `relatedAgents`, `version`, `prerequisiteCommand`) and deliberately omits server-only internal handler fields.

## Skills

- `/api/skills` — CRUD for skills (GET, POST)
- `/api/skills/[skillId]` — Skill detail (GET, PATCH, DELETE). PATCH accepts optional audit `note` and writes the previous row to `skill_revisions` before applying updates.
- `/api/skills/[skillId]/revisions` — Skill revision history (GET). Returns `{ revisions }` newest-first, each with raw JSON `snapshot`, parsed `parsedSnapshot`, `author`, optional `note`, and `createdAt`.
- `/api/skills/[skillId]/revert` — Revert a skill to a prior revision (POST: `{ revisionId }`). The current row is first recorded as a new revision, then the selected snapshot's name, description, and content are restored.

## Projects

- `/api/projects` — All projects list (GET)
- `/api/projects/runtime` — Per-project runtime snapshot for the projects table (GET). Returns `{ projects }`, keyed by project name. Each value contains running-state flags (`hasRunningReview`, `hasRunningTest`, `hasRunningRelease`, `hasRunningPipelineChild`), `runningCount`, distinct `runningKinds`, `runningAgentNames`, the latest finished review verdict (`latestVerdict`, `latestVerdictAt`), `lastActivityAt`, and a compact `lastJob` object with camelCase fields (`id`, `kind`, `status`, `exitCode`, `startedAt`, `finishedAt`, `verdict`). The route is intentionally summary-only; use `/api/jobs` for paged run rows and `/api/jobs/counts` for aggregate totals.
- `/api/projects/personas` — File-based skills from `skills/docs/skills/` (GET)
- `/api/projects/[schedId]/priority` — Set project scheduling priority (PATCH: `{ priority }`, one of `critical`, `high`, `medium`, `low`). Returns `200 { status: 'ok' }`, `400 { detail: 'invalid JSON body' }` for malformed JSON, `422 { detail }` for unsupported priority values, or `404 { detail }` when the scheduler project is unknown.
- `/api/projects/[schedId]/detail` — Project scheduling detail (GET). Returns `200 { id, project, job, prompt_path, prompt_content, memory_path, memory_content, persona, run_history }`, where `run_history` is the newest 20 jobs for that scheduler id with `{ started, ended, duration_s, exit_code }`; unfinished jobs use `null` for `ended`, `duration_s`, and `exit_code`. Returns `404 { detail }` when the scheduler project is unknown.
- Project pause/resume is handled by `PATCH /api/projects/by-project/[name]` via the `paused` flag; there is no standalone pause/resume route.
- `/api/projects/[schedId]/retrieval/reindex` — Re-index the project retrieval corpus (POST). The corpus includes committed project docs, DB-backed skills referenced by that project's agents, and synthesized project config guidance. Returns `200 { chunks, indexedSources, skippedSources, diagnostics }` on success, where `diagnostics` includes pre-reindex `missingSourcesBeforeReindex`, `staleSourcesBeforeReindex`, and per-source counts. Returns `400 { error }` when retrieval is disabled and `404 { error }` when the project is unknown. The retrieval store is `retrieval_chunks` on the same Postgres instance as the rest of TamTam (pgvector-backed `embedding vector(768)` column); the `vector` extension must be installed (the initial migration creates it).
- `/api/projects/[schedId]/retrieval/stats` — Lightweight retrieval corpus counts for one project (GET). Returns `200 { records, chunks }`, where `records` is the number of `retrieval_records` rows and `chunks` is the summed chunk count for the project.
- `/api/config/projects` — Workspace project discovery and bulk configuration (GET, PATCH). `GET` reads the `workspace_path` setting, expands `~`, scans only first-level visible directories for `.git`, skips common build/dependency directories (`node_modules`, `.next`, `.git`, `dist`, `build`, `.venv`, `__pycache__`), sorts discovered repos by name, and merges saved state. Returns `200 { workspace_path, projects }`, where each project has `{ name, path, enabled, github, priority, archived, custom_actions }`; missing or unreadable workspace paths return an empty `projects` array. `PATCH` accepts `{ projects: [{ name, path, enabled, github?, priority?, custom_actions? }] }`, upserts each row, stores `custom_actions` as JSON, and returns `200 { status: 'ok' }`; non-array `projects` returns `400 { detail: 'projects must be an array' }`. Projects newly transitioning to enabled trigger best-effort built-in system-agent seeding after the rows are persisted; seeding failures are logged but do not fail the request.

## Project actions (`by-project/[name]/...`)

- `` (root) — `PATCH /api/projects/by-project/[name]` updates the project `archived` and/or `paused` flags. Body accepts `{ archived?: boolean, paused?: boolean }`; at least one field must be present. Returns `200 { project, archived, paused }` (both fields always present regardless of which was updated); `400` when neither field is provided or when a provided field is not a boolean; `404` when the project row does not exist. Archiving a project clears the in-memory project-data cache and removes any in-memory scheduled-agent timers belonging to that project; unarchiving is a metadata-only update. While `archived` is true the project is hidden from the default `/api/projects` list, the internal scheduler skips its agents, and `/api/projects/by-project/[name]/release` (and `startRelease`) return `409 { detail: 'project archived' }`. While `paused` is true the internal scheduler skips scheduled agent fires for that project, `/api/agents/[agentId]/run` returns `409 { code: 'project_paused', detail }`, and `startRelease` returns `409 { detail: 'project paused' }`; manual terminal sessions are unaffected. Pausing does not remove scheduler entries — fires resume automatically when `paused` is toggled back to false.
- `action` — Custom actions (GET, PUT, POST). POST is pause-gated and returns `409 { detail }` when `jobs_paused` is enabled globally.
- `setup` — New-project onboarding wizard state and detection (GET, PATCH). GET returns `{ project, setup_complete, setup_state, detection }`, where `setup_state` records per-step `completed` / `skipped` for `detect`, `pipeline`, `automation`, `notifications`, `file_config`, and `smoke_test`. Detection reuses existing test-command/default-branch helpers and bounded git/gh probes for GitHub remote, `gh auth`, and `.github/workflows` presence. PATCH accepts `{ step, status }` for independent step persistence, `{ setup_complete }` to finish or reopen setup, and `{ write_file_config: true, test_command?, safe_users? }` to write the team-shareable `.tamtam/config.yml` subset through `writeFileConfig`.
- `config` — Project test command + file-backed release timeout override (`release_timeout_minutes`) + DB-backed pipeline toggles (`test_cron_enabled`, `auto_commit_enabled`, `auto_push_enabled`, `auto_pr_merge_enabled`, `release_after_run`, `tests_disabled`, `review_disabled`, `issue_auto_branch`) + settings-backed `quarantined_tests: string[]` for known flaky test IDs + per-project review/fix prompt controls (`review_prompt_addendum`, `review_prerequisite_command`, `fix_prompt_addendum`) + DB-only QA target URLs (`website`, `qa_url`) + DB-only dev-server lifecycle fields (`dev_server_start_command`, `dev_server_stop_command`, `dev_server_ready_url`) + DB-only spend caps (`daily_spend_cap_usd`, `release_spend_cap_usd`) and read-only `last_24h_spend_usd` + file-backed commit-message style override (`commit_style`) (GET, PATCH). `review_prerequisite_command` is a bash command run from the project root before each review; `.tamtam/config.yml` `pipeline.review_prerequisite_command` overrides the DB fallback on read, and PATCH stores local edits in the DB. `quarantined_tests` accepts an array of exact test IDs parsed from failed vitest/pytest output; when all failures are quarantined, the release test step records `quarantined` outcomes and continues. `website` is the per-project public URL for the QA agent to browse; `qa_url` is an explicit QA target that takes precedence over `website`. Both URL fields are trimmed, accept only `http://` or `https://`, and clear the stored value on empty string. `dev_server_start_command` is a `bash -c` command run from the project root at agent kickoff when set. `dev_server_stop_command` is optional and, when set, is run from the project root before TamTam falls back to terminating the owned process group. `dev_server_ready_url` is optional, trimmed, accepts only `http://` or `https://`, and is polled until it returns a non-5xx response; empty string clears the stored value. Spend caps accept non-negative USD numbers and clear on empty string or `0`; `daily_spend_cap_usd` blocks new agent runs and Release starts once rolling 24h project spend reaches the cap, while `release_spend_cap_usd` stops an active Release at the next phase boundary once release child-job spend reaches the cap. These dev-server and spend-budget fields are DB-only local operator metadata and are not written to `.tamtam/config.yml`. `pr_workflow_enabled` is no longer part of this route contract; push-vs-PR behavior is derived from the checked-out branch at runtime. `release_timeout_minutes` is stored in `.tamtam/config.yml` under `pipeline.release_timeout_minutes`; empty string clears the project override so Release runs fall back to the global `release_wall_clock_timeout_minutes` setting. `commit_style` is stored in `.tamtam/config.yml`; empty string clears the project override so commit generation falls back to the global setting.
- `run` — Run Claude on project (POST, accepts `model`, optional `provider`, and optional `permissionMode` params). `permissionMode` overrides the global `permission_mode` setting for this run only (one of `acceptEdits`, `auto`, `bypassPermissions`, `default`, `dontAsk`, `plan`; unknown values return `400 { detail }`); the terminal toolbar's `perms` dropdown drives it. When `provider` is supplied, TamTam treats it as a required CLI choice for that run and returns `409`/`429` instead of falling back to another provider if the selected one is disabled or over budget. Before creating a job, the route estimates the composed prompt, including selected personas, auto-attached docs, base prompt/project memory, issue context, and attachment path instructions; accepted responses include `prompt_estimate`, while oversized prompts return `413 { code: 'prompt_estimate_blocked', detail, prompt_estimate }` before any job row or provider process exists. When another job is already running for the project, the run is **queued** (not rejected): returns `202 { status: 'queued', queueId, position, blockingKind, blocking_job_id }` and the raw request is persisted to `queued_terminal_runs`. It drains FIFO when the blocker clears — ahead of any queued agent (user input has priority) — and the originating terminal polls `queued-runs/[queueId]` to attach the live stream once it starts. The internal drain replays the payload with header `x-tamtam-terminal-drain: <queueId>`; on that replay a still-running blocker returns `409 { detail, blocking_job_id }` (no re-enqueue) so the queue row is retried on the next finish-seam. The JSON body also accepts `attachmentPaths: string[]`, honored **only** on a drain replay (header set) and **only** for paths that `realpath`-resolve inside `data/attachments/` — the containment check, not the client-settable header, is the security boundary against arbitrary-file reads. Manual terminal runs bypass `jobs_paused` — the global pause does not block this endpoint.
- `queued-runs/[queueId]` — Status/cancel of a queued terminal run. `GET` returns `{ status: 'pending'|'started'|'gone', jobId }` (the terminal polls until `started`, then streams `jobId`); `gone` means the row was drained-and-pruned or never existed. `DELETE` cancels a still-pending queued run, returning `{ cancelled: boolean }`; `404` when the row belongs to a different project.
- `prompt-insights` — Recent prompt composition and retrieval diagnostics for the project overview (GET, optional `?days=N`, default `7`, allowed `1..90`). Returns `200 { windowDays, agentJobCount, promptBytes, retrieval, memory, prereq }`, where `promptBytes` is `null` when no prompt sizes are available and otherwise includes `avg`, `p50`, `p95`, and `max`; `retrieval` aggregates structured `contextMeta.retrieval` samples from `agent:*` jobs; `memory` aggregates structured `contextMeta.composition.memory`; and `prereq` counts structured `composition.hasPrereq` values. Returns `400 { error }` when `days` is outside the allowed range.
- `review` — Start AI code review (POST)
- `review-pr` — Start AI review of a GitHub PR (POST: `{ prNumber, prTitle?, headRef?, baseRef? }`, where `prNumber` must be a positive integer). PR review prompts ignore `.tamtam/` metadata changes unless the review is explicitly about TamTam configuration.
- `address-pr-comments` — Dispatch a Claude job to address a human reviewer's unresolved PR comments, push a fix commit, and reply on each thread (POST: `{ pr }`, where `pr` must be a positive integer). Returns `200 { status: 'started', job_id, pid, log_path }`. Fetches inline comments (`gh api pulls/:n/comments`, grouped by file + diff hunk) and top-level reviews (`gh pr view --json reviews`); external comment text is wrapped as untrusted input. Returns `400` when there are no unresolved comments, `409 { blockingJobId }` when an address-run is already in flight for the project, and `429` when the `3 / 30 min` fix-loop cap is hit. See `docs/PIPELINE.md` → "Addressing human PR review comments".
- `fix-ci` — Start AI CI fix run (POST). Returns `409 { detail, blocking_job_id }` when another job is already running for the project
- `resolve-conflicts` — Operator-initiated automated merge-conflict resolution for an open PR branch (POST: `{ prNumber }`, positive integer). Explicit-consent counterpart to the inbox "Resolve conflicts" HITL. Resolves the PR head/base via `gh`, refuses unless it is an OPEN, still-CONFLICTING PR (`409`/`404`), fetches the base, checks out the branch (refusing a dirty worktree, `409`), runs the PR-branch author-trust gate (`checkPrBranchExecutionGate`, `409` on an untrusted-authored branch), then spawns a `resolve-conflicts` agent job that rebases onto the freshly-fetched `origin/<base>` and resolves the hunks to a clean tree **without pushing**. On job completion `finalizeResolveConflicts` independently re-validates the rebase (clean tree, no markers, `behind==0`, `ahead>0`, PR still open) and only then `git push --force-with-lease`es and re-dispatches `pr-wait`; any failure aborts to a clean tree and re-raises the conflict HITL (merge-or-HITL). Returns `200 { status: 'started', job_id, pid, log_path, pr_number, branch }`, or `409 { detail, blocking_job_id? }` when a resolve or another job is already running. See `docs/SECURITY.md` → "Operator-initiated conflict resolution" and `docs/PIPELINE.md`.
- `test` — Run project test command (POST). Body may include `{ approveUntrustedPrBranch?: true }` to explicitly allow a host-side test run on a non-default branch whose current checkout cannot be fully verified through GitHub. Without that approval, non-default branches return `409 { detail }` when branch detection fails, the worktree has uncommitted/untracked changes, or any branch commit cannot be mapped through GitHub to a trusted `author.login` in `safe_users` / `trusted_github_users`.
- `behind` — Lightweight upstream divergence check (GET). Refreshes the configured upstream ref and returns `200 { behind, ahead }`; projects without an upstream return zeros.
- `changes` — Uncommitted changes summary (GET, returns `defaultBranch`/`branch`/`branchMerged`/`ahead`/`behind`/`openPrUrl`/`files` plus totals); git pull with strategy (POST: `ff-only`/`merge`/`rebase`). Pull returns `400 { detail }` for unknown strategies, `409 { detail, diverged: true }` on branch divergence, and `409 { detail }` when the working tree has tracked or untracked local changes, so callers must commit or stash before pulling.
- `changes/diff` — Full git diff content for one project-relative file (GET: `?file=<path>`). Returns `400 { detail }` when `file` is missing or resolves outside the project.
- `checkout-default` — Switch to default branch; refuses if uncommitted changes (POST → `{ status: 'switched'|'already-on-branch', branch }`)
- `push` — Push changes to git (POST). Accepts optional JSON body `{ commit?: boolean, release_id?: string }`: `commit: true` runs the commit step first; `release_id` keeps manual push retries linked to the active release chain and allows History to re-run the failed push for the latest finished release on that project; with `commit: true`, it allows History to re-run the failed commit instead.
- `create-pr` — Push current branch + create GitHub PR (POST → `{ url }`). Accepts optional JSON body `{ force?: boolean }`; `force: true` retries with `git push --no-verify` to skip the local pre-push hook after an explicit user confirmation flow. Refuses on the default branch. Returns `409 { detail, hookFailure: 'pre-push-tests'|'pre-push-other', retryable: true }` when a retryable pre-push-hook failure blocks the initial push; non-hook push failures remain `500`.
- `pr-wait` — Start PR merge polling for an existing PR (POST: `{ prNumber, prRepo?, prUrl? }`). When `prRepo` or `prUrl` is omitted, the route resolves them with `gh pr view`. Returns `200 { status: 'started', jobId, prNumber, prRepo, prUrl }`; returns `409 { error: 'jobs paused' }` when `jobs_paused` is enabled globally; returns `502` when PR identity lookup through `gh` fails.
- `release` — Trigger release pipeline (POST). Accepts optional `{ queue_if_blocked?: boolean, source_job_id?: string }`; `source_job_id` is applied only to the immediate release attempt, while queued retries are project-scoped pending-release flags and do not retain that source job metadata. Returns `200 { status: 'started', step, job_id?, release_job_id?, message }` when the first pipeline step starts, `202 { status: 'queued', message, blocking_job_id? }` when `queue_if_blocked` defers behind active project work, standard pre-flight `4xx { detail, blocking_job_id? }` failures from `startRelease`, `413 { detail }` when the first review/fix prompt estimate exceeds `prompt_estimate_block_tokens` before the provider starts, or `500 { detail }` when the workflow runtime cannot enqueue the release.
- `release/plan` — Side-effect-free dry-run of the release pipeline (GET). Returns the ordered steps the Release button *would* run for the project's current branch/state/config without running any of them: no git writes, no job creation, no PM2 start, no GitHub mutation, no webhook send. Returns `200 ReleasePlan` with `{ project, canRelease, blockers[], mode: 'pr'|'direct', currentBranch, targetBranch, comparisonRange, entryStep, steps[] }`, where each step is `{ kind, willRun, reason, sideEffects[], comparisonRange? }` over the canonical order `test → review → commit → push → mark-dod → pr-wait → soak`. `blockers[]` carries read-only preconditions (`archived`, `paused`, `nothing_to_release`, `job_running`, `pipeline_running`, `pr_wait_open`). Reuses the same decision helpers as `startRelease` plus the `decideNextPhase` transition matrix; runtime-only gates (CLI start gate, provider budget, readiness `prerequisiteCommand`) are intentionally not evaluated because they can have side effects. Returns `404 { detail: 'project not found' }` for an unknown project and `500 { detail }` on unexpected failure. See `docs/PIPELINE.md` → "Release plan (dry-run)".
- `release/[releaseId]` — Release detail: meta-job + ordered pipeline step jobs with verdicts and log excerpts (GET). Uses the shared release timeline builder, including display-only `mark-dod-verify` jobs.
- `release/[releaseId]/resume` — Manually resume a finished release whose pipeline chain stopped at a non-terminal successful step (`test`, `fix`, `review`, or `commit`) before the next step was spawned (POST). Returns `200 { status: 'resumed', release, project, resumedFrom }` after re-acquiring the project pipeline lock, reopening the release row, and re-firing the last step's completion hook. Returns `404` when the release does not exist for the project, `409` when the release is still active, has no resumable step, the last step is terminal/failed, another active release already owns the project lock, or any other same-project pipeline step is still running (`blocking_job_id` included for busy conflicts), and `500` when lock re-acquisition or hook launch fails. Failed hook launches roll the release row back to its original finished state and release the lock.
- `release/abort` — Abort active release (POST). On the fast path it marks the release aborted, stops the running step, finalizes the release, and releases the lock. If the active inline `commit`/`push` step acknowledges cancellation but does not unwind within 20s, it returns `409 { status: 'abort_pending', detail, release_id, killed_job_id: null }`; the late step completion then finalizes the release as aborted, stops the monitor, and releases the lock without requiring a second abort request.
- `issues` — GitHub PRs and issues (GET, with `?refresh=1` to bypass cache). `?trusted_only=1` filters the returned `issues` array server-side to authors trusted by the union of global `trusted_github_users` and per-project `.tamtam/config.yml` `security.safe_users`; the `prs` array is left untouched. By default the response is slim: each issue is stripped to `{number, title, labels, author, url, hasContext}` and each PR to `{number, title, labels, author, url, branch, isDraft, gates}`. Pass `?full=1` to include `body`, `assignees`, and all other raw fields (with `hasContext`/`gates` still folded in). `hasContext` and `gates` are computed server-side in one pass over the in-memory jobs cache and the already-fetched issue bodies, so the Issues tab renders the Continue badge and PR gate badges without the former per-row `continue-issue`/`pr-gates` request fan-out (previously one HTTP call per open issue and PR). DoD in `gates` is derived from the linked issue's body already present in the payload — no extra `gh issue view` per PR; a PR linked to an issue outside the open set reads `dod: 'none'`. Pass `?summary=1` for the project header polling shape: `{ repo, prCount, issueCount, openPrBranches, error, cached, cachedAt }`, where `openPrBranches` contains `{ branch, number }` for each open PR. Pass `?pick_top=1` for the issue-cruncher prerequisite shape: `{ chosenIssue, issue, branch, openPr, reason, cached, cachedAt }`, where `issue` contains one trusted-author issue body plus comments that are trusted at response time, and `branch` is `{ name, status }` after TamTam creates/reuses/checks the issue branch or `null` when auto-branching is disabled/skipped. `openPr` is `{ number, branch, url }` when an open PR already implements the chosen issue (matched by canonical `fix/issue-<n>` branch, structured closing reference, or close-keyword in the PR body); in that case TamTam checks out the PR's branch instead of a fresh fix branch so the cruncher can verify-and-merge it (via the `merge-pr` agent action) rather than re-implement, else `openPr` is `null`. Branch checkout failures return `chosenIssue: null` with `reason` such as `branch_pipeline_running: <jobId>`, `branch_creation_failed: <detail>`, or `pr_branch_checkout_failed: <detail>`. `pick_top` excludes blocker labels (`blocked`, `needs-info`, `needs-design`, `needs-refinement`, `discussion`, `question`, `wontfix`, `duplicate`, `human-needed`) and assigned issues, ranks eligible trusted-author issues by priority labels then `updatedAt`, fetches the chosen issue detail with `gh issue view`, caches the filtered detail in `gh_issue_detail_cache` for 5 minutes, revalidates cached issue/comment authors against the current trust allowlist before every response, and checks out the issue branch before returning a successful pick. POST accepts `{ prNumber, action?: 'merge'|'approve', mergeMethod?: 'merge'|'squash'|'rebase' }`. Before acting, POST resolves the PR author via `gh` and refuses with `403 { detail, untrustedAuthor }` unless that author is in the union of global `trusted_github_users` and per-project `.tamtam/config.yml` `security.safe_users` — on a public repo anyone can open a PR, so a merge/approve must not land untrusted code (fail closed when the author can't be resolved; add the author to trust or act on GitHub directly to override). Approve returns `{ status: 'approved', pr, repo }`, while merge invalidates the issue cache, switches the working copy to the default branch, and returns `{ status: 'merged', pr, repo, switchedTo }` or `207 { status: 'merged_dirty', pr, repo, switchedTo: null, switchError }` when post-merge checkout cleanup fails.
- `issue-comment` — Post a GitHub issue comment (POST: `{ number: number; body: string }`). Resolves the repo from project GitHub config / origin / settings, runs `gh issue comment`, invalidates `gh_issue_detail_cache` for that issue, and returns `{ status: 'commented', number, repo }`; returns `422` when `gh` fails.
- `issue-close` — Close a GitHub issue (POST: `{ number: number; reason: 'completed' | 'not planned'; comment?: string }`). Resolves the repo from project GitHub config / origin / settings, runs `gh issue close`, invalidates the issue detail cache and project issue list cache, and returns `{ status: 'closed', number, reason, repo }`; returns `422` when `gh` fails. Besides the agent action orchestrator, this route is surfaced in the **Issues tab** as the per-row and drawer **Close** control (a reason picker — `completed` / `not planned` — plus confirm/cancel) via the `closeIssue` client helper (`lib/client/projects.ts`); on success `IssuesTab` optimistically drops the row, updates the count, and refetches (`components/issues-tab/CloseIssueControl.tsx`).
- `issue-label` — Add or remove GitHub issue labels (POST: `{ number: number; addLabels?: string[]; removeLabels?: string[] }`). Labels are limited to GitHub-safe names; added labels are created with the default `FBCA04` color when missing. On success it invalidates the issue detail cache and project issue list cache, then returns `{ status: 'labeled', number, repo, addLabels, removeLabels }`; returns `422` when label creation or issue edit fails.
- `issue-branch` — Create or checkout `fix/issue-<n>-<slug>` before Claude edits (POST: `{ issue_number: number, issue_title?: string }`). Returns `{ status: 'created'|'reused'|'already-on-branch', branch }` when checkout succeeds, `{ status: 'skipped', reason, branch? }` when project policy or merged-branch protection blocks checkout, `409 { detail, blockingJobId }` when a release pipeline currently owns the project lock, `400` for invalid JSON or missing `issue_number`, `404` when the project is unknown, and `500 { detail }` when git checkout fails.
- `continue-issue` — Build a "Continue work" payload for an issue (GET: `?issue_number=N`); returns `{ sessionId, provider, prompt, unverifiedCount, hasContext }`
- `issues/[number]/close-stale` — Post a verdict comment then close the issue (POST: `{ findings: string; reason?: 'stale' | 'duplicate' | 'wontfix' | 'fixed' }`). `reason` defaults to `stale`; `fixed` maps to GitHub state-reason `completed`, everything else maps to `not_planned`. Returns `{ status: 'closed', issue, repo, reason, verdict }`; `502` when the `gh` CLI calls fail.
- `mark-dod` — Run DoD verification for the latest release-linked issue or PR context (POST). In the default workflow-driven release the orchestrator routes `push → mark-dod` unconditionally, so DoD runs and ticks the issue's acceptance criteria before `pr-wait` — and before any `risky_diff` / `merge_permanent` HITL — regardless of the auto-merge setting; `mark-dod → pr-wait` then follows only when `auto_pr_merge_enabled` is on and a PR exists (else the release finalizes after `mark-dod`). Only the legacy completion-hook chain (standalone no-`releaseId` steps in `lib/jobs/lifecycle.ts`) defers DoD to post-merge, auto-triggering after review→LGTM and after successful PR-producing pushes when auto-merge is off
- `pr-branch` — Fetch and checkout a PR's head branch (POST: `{ branch }`)
- `pr-gates` — TamTam-side gate state for a single PR (GET). Accepts `?issue=N` or parses `?body=` for `Closes/Fixes/Resolves #N`; `?repo=owner/name` enables the DoD lookup through `gh issue view`. Returns `{ issueNumber, tests, review, dod, dodSummary }`, where gate values are `pass`, `fail`, `warn`, or `none`; returns `404 { detail: 'project not found' }` when the project is unknown. The Issues tab no longer calls this per row — it reads `gates` folded into the `issues` response — but the endpoint stays for standalone lookups. Shares its gate/DoD logic with `lib/github/issue-row-enrichment.ts`.
- `branch` — Current + default branch (GET → `{ branch, defaultBranch, commitsAhead }`); no `git fetch` issued
- `behind` — Ahead/behind commit counts vs remote (GET)
- `logo` — Repo-local project logo asset (GET). Detects a repo-local image from a small built-in allowlist of common paths such as `.tamtam/logo.*`, `public/logo.*`, `public/icon.*`, `public/favicon.*`, `app/icon.*`, `src/app/icon.*`, and root-level `logo.*`, then streams that file with the matching image content type. Returns `404` when the project is unknown; known projects without a supported local logo return a generated `image/svg+xml` placeholder.
- `logs` — Project run log files (GET)
- `docs` — Project documentation files (GET). Returns `200 { docs }`, where each entry has `{ name, path, content }`. The route includes the first readable root README candidate (`README.md`, `readme.md`, or `Readme.md`) as canonical `name: "README.md"` first, then top-level `docs/*.md` files sorted alphabetically; subdirectories and non-Markdown files are ignored. Known projects without matching docs return an empty array, and unknown projects return `404 { detail: 'project not found' }`.
- `initiatives/preview` — Preview initiative candidates for a project without persisting them (GET). Runs the live probes (`runProbes`) against the project path and passes findings through `mineCandidates`. Returns `200 InitiativePreviewResponse { project, generatedAt, candidates: [{ kind, title, rationale, score, dedupKey }] }` (slim shape; `prompt` is omitted). Returns `404 { detail: 'project not found' }` when the project is unknown; `500 { error }` on unexpected probe failures.
- `recommendations` — GET; PATCH `{ id, status }` to update non-terminal state (`open` or `dismissed`). The GET response can include terminal `status: "resolved"` rows when TamTam has automatically retired a recommendation after the triggering condition cleared; PATCH still accepts only `open` and `dismissed`. Recommendation rows include the common fields from the `recommendations` table plus a parsed JSON `payload`. For `agent_schedule_backoff`, the payload includes `currentSchedule`, `recommendedSchedule`, `reason`, `confidence`, and an optional `reasoning` object with `{ summary, actionableWork, filesChangedCount, currentSchedule, recommendedSchedule, confidence, sourceJobId }` when the agent run report provided enough detail to explain the backoff suggestion in the UI. For orchestrator-generated `orchestrator_agent_health`, the payload includes `concern`, `concernType`, `severity`, `llmSummary`, `llmRecommendation`, `runsAnalyzed`, `runIds`, `lastRunScore`, and `avgRunScore`; these recommendations are informational and dismiss-only.
- `recommendations/apply` — Apply an auto-applicable recommendation server-side (POST `{ id }`). Validates the recommendation is still `open`, performs the underlying mutation, then marks the row `applied`; returns `400 { detail }` when a schedule recommendation targets a system agent because its schedule is Settings-managed, and `409 { detail }` when the recommendation is stale/non-open

## Jobs / Runs

- `/api/automation-queue` — Deferred automation queue (GET). Accepts optional `project=<name>` and returns `{ items }` for pending release flags and DB-backed queued agent runs. Each item includes `id`, `project`, `kind` (`pending_release` or `queued_agent_run`), `reason`, `code`, `queuedAt`, `blockingJobId`, `nextRetryState`, `retryAllowed`, and `cancelAllowed`; queued-agent rows also include `agentId`, `agentName`, and `triggeredBy`. Old pending-release flags created before queue timestamps report `queuedAt: null`.
- `/api/automation-queue/cancel` — Remove a safe deferred automation item without stopping active jobs (POST: `{ kind, project, id? }`). `pending_release` clears only that project's pending-release flag; `queued_agent_run` deletes only the matching DB row for the project. Returns `200 { status: 'cancelled' }`, `400` for malformed input, `404` when the item no longer exists, or `500 { detail }` when cancellation fails.
- `/api/automation-queue/retry` — Run the same ordered recovery drain used by boot/resume/recovery for a project (POST: `{ project }`). Pending releases are retried before queued agents, preserving pipeline ordering. Returns `{ status: 'started'|'stayed_queued'|'empty', items }`, where `items` is the remaining queue after the drain attempt; returns `400 { detail: 'project is required' }` when `project` is missing or blank.
- `/api/inbox` — Cross-project triage feed (GET). Read-only aggregation over the project-data cache, the jobs cache, the automation queue, and the gh issues cache — no new background work and no live GitHub calls. Returns `{ signals, counts }` where `counts` is `{ red, yellow, green, total }` and each signal includes `id` (stable `type:project`), `type` (`ci_red` | `review_needs_decision` | `pr_ready_to_merge` | `pr_conflicts` | `pr_needs_manual_merge` | `stale_changes` | `fix_loop_exhausted` | `orphan_release` | `project_paused`), `severity` (`red` | `yellow` | `green`), `project`, `title`, `detail`, `href` (open-project link), `externalUrl` (e.g. failed CI run), `ageSeconds`, and `action` (`{ kind, label, prNumber? }`). Every action resolves through an existing per-project endpoint (`release` / `review` / `fix-ci`, PR `merge`, `resolve-conflicts`, `resume`, or `automation-queue/retry`); the `open-terminal` action is a navigation link. A `pr_conflicts` signal (or a `pr_needs_manual_merge` whose `prWaitReason` is `conflict`) carries the `resolve-conflicts` action, which POSTs to the project's `resolve-conflicts` endpoint to auto-rebase + resolve rather than offering a doomed one-click `merge`. `pr_needs_manual_merge` (yellow, `merge` action) is raised when the `pr-wait` phase deliberately deferred auto-merge to a human — `risky_diff` (diff touches high-risk execution files) or `merge_permanent` (merge blocked) — and the PR is still open; the reason is read from `prWaitReason` stamped on the pr-wait job's `contextMeta`, and the signal self-clears once the PR is merged/closed. Because DoD verification runs before `pr-wait` in the orchestrator path, this signal's `detail` also carries a DoD summary (`DoD: X/N acceptance criteria verified on issue #I`, or `Linked issue #I.` when the issue has no criteria) so the operator can see the linked issue and what the model verified before deciding to merge — the pr-wait job is joined to its release's `mark-dod` by shared `release_id`, and the derivation exposes `releaseId`, `dodVerified`, `dodTotal`, and `dodIssueNumber` on the projected job (`lib/workflows/inbox.ts` → `latestDodForRelease` / `dodDetailSuffix`). Taking its `merge` action also resumes the project after the merge (a manual-merge HITL means the pipeline was stalled on that decision — merging it is "ship and continue"). The `fix_loop_exhausted` catch-all (a release that finished non-zero without shipping) is likewise suppressed once the release's PR shipped via a merge — a merged pr-wait at/after the failed release's start counts as the "merged" arm of the merge-or-HITL invariant — so a risky-diff defer you later merge from the inbox stops showing a stale "Release stopped" once it's merged. Signals for a project whose pipeline is actively running are suppressed. `?project=<name>` narrows the feed to a single project's signals with `counts` recomputed for that subset — this powers the per-project "Needs your decision" banner on `/project/<name>` (`components/project-detail/ProjectSignals.tsx`). The unfiltered feed powers the `/inbox` page and the header's urgent-count badge.
- `/api/attention` — Unified Inbox feed (GET). Read-only merge of the derived inbox signals (`listInboxSignals()`, repo shippability) and the open recommendations (`listAllOpenRecommendations()`, agent quality), each mapped by the pure adapters in `lib/attention/map.ts` into one `AttentionItem` shape and interleaved by `mergeAttention()`. Returns `{ items, counts }` where `counts` is `{ red, yellow, green, total }`. Each item has `id` (namespaced `signal:<inboxId>` | `rec:<recId>`), `source` (`signal` | `recommendation`), `project`, `severity` (`red` | `yellow` | `green` — red is reserved for shippability blockers; a recommendation is never red: MANUAL → yellow, AUTO → green), `title`, `detail`, `ageSeconds`, `href`, `externalUrl`, `actions` (one action for a signal; the type/payload-derived Fix-menu set for a recommendation, via `recommendationActions`), `agent` (`{ id, name }` for recommendations, else null), and `dismissible` (recommendations true; signals self-clear). Sort is `red → yellow → green`, then oldest-first, then project. `?project=<name>` narrows both sources. Actions dispatch to the existing per-project inbox/recommendation endpoints — this route adds no mutation surface. Powers the merged `/inbox` page (primary tab) and the header urgent-count badge (red only). `500 { detail }` if a source throws.
- `/api/jobs` — Paged runs across projects (GET). Query params: `project=<name>` filters by project, `kind=<kind>` filters by exact job kind, `kind_prefix=<prefix>` filters by kind prefix such as `agent:`, `status=running|done|aborted` filters by lifecycle status, `from=<epoch_seconds>` / `to=<epoch_seconds>` bound `started_at`, `limit=<n>` controls page size, and `offset=<n>` skips rows after filtering and newest-first sorting. `limit` defaults to 30, `limit=0` is capped to 200 for legacy callers, and all explicit limits are capped at 200. Returns `{ jobs, total, offset, limit, nextOffset, pendingReleaseProjects }`; `total` is counted after filters and before the page slice. Row payloads are list-oriented: `prompt` and `user_prompt` are previews, `log_path` is omitted, and failed non-cancelled rows may include a compact `detail` extracted from the job log so list views can show the terminal failure reason without opening the full job detail. Use `/api/jobs/[jobId]` when a caller needs the full prompt, log path, or display log.
- `/api/jobs/counts` — Aggregate run totals without row payloads (GET). Accepts the same `project`, `kind`, `kind_prefix`, `from`, and `to` filters as `/api/jobs`. Returns `{ total, byKind, byStatus, tokens, cost }`, where `byStatus.failed` uses the same review-verdict attention rules as the runs UI and `cost.monthToDate` is scoped to the current calendar month.
- `/api/jobs/notifications` — Compact notification payload for the bell (GET). Returns `{ count, jobs, runningCount, runningJobs }`, where `count` is the full unsuperseded unseen-finished total and `runningCount` is the full running total before payload caps. `jobs` and `runningJobs` each include only the newest 50 lightweight rows; use `/api/jobs` or `/api/jobs/[jobId]` for paged or full job data.
- `/api/jobs/[jobId]` — Job detail (GET, DELETE). `GET` returns a display-oriented `log`: `release` jobs return the raw aggregated log verbatim, while other jobs return parsed Claude output with any non-NDJSON passthrough lines (for example agent prerequisite output) preserved ahead of the parsed stream. Failed jobs may include `detail` only when the log has no replayable human-readable failure output (missing/empty/wrapper-only logs, or JSON-only logs without a final result); plain-text failure output is returned in `log` instead of repeated in `detail`. `DELETE` cancels unfinished jobs: inline `commit`/`push` jobs and jobs with a registered cancellation signal stop cooperatively with a 20s timeout (`409 { detail }` on timeout), while eligible child-process jobs receive `SIGTERM` followed by `SIGKILL`; suspicious low PIDs are refused.
- `/api/jobs/[jobId]/logs` — Job log content (GET)
- `/api/jobs/[jobId]/trace` — Full trace of one work unit for the history detail drawer (GET). Resolves the unit (any job kind), its trigger (parent) job, and the release it is or owns/belongs to, returning `{ job_id, project, kind, prompt, status, exit_code, started_at, finished_at, duration_ms, verdict, session_id, release_id, trigger, steps, workSummary, files, usage, context, logExcerpt, logPruned }`. `steps` are the release's ordered pipeline phases with per-step verdict and log excerpt, built by the shared `buildPipelineSteps` helper and inclusive of the display-only `mark-dod-verify` job. `files` is `{ files, linesAdded, linesRemoved }`, `usage` bundles token/cost/prompt-byte/model/provider, and `context` carries `{ skills, releaseStopReason, outcomeVerdict, followupIssueUrl, followupIssueNumber, runScore }`. Returns `404 { error: 'job not found' }` for an unknown job id. Read-only.
- `/api/jobs/[jobId]/resources` — CPU/RSS samples collected by the background probe sweep for a job (GET). Returns `{ jobId, samples: [{ t, cpu, rss }] }`, where `t` is the Unix timestamp in seconds, `cpu` is process CPU percent, and `rss` is resident memory in KB. Accepts optional `?since=<unix_seconds>` to return samples with `sampled_at >= since` and optional positive integer `?limit=<n>`; the default is 1000 and explicit values are capped at 5000. Invalid query parameters return `400 { detail }`; unexpected database failures return `500 { detail }`.
- `/api/jobs/[jobId]/board-sync` — Manually sync a finished root job to the GitHub project board (POST); rejects running jobs, requires board sync configured, surfaces GitHub failures instead of swallowing them
- `/api/jobs/[jobId]/rerun` — Re-run a job (POST). Returns `409 { detail, blocking_job_id }` when another job is already running for the project
- `/api/jobs/[jobId]/fix` — Start AI fix run for a failed job (POST)
- `/api/jobs/[jobId]/continue` — Resume a finished `run` or `agent:*` job's CLI session via `--resume <sessionId>` (POST). Rejects non-resumable kinds (`400`), jobs without a usable `sessionId` in the row or log tail (`400`), jobs with a resume session but no recorded CLI provider (`409`), still-running jobs (`409`), and jobs finished more than 30 minutes ago (`410`) since the provider session cache and first-invocation context (skills/docs/retrieval) are no longer reliable past that window. Returns `409 { detail, blocking_job_id }` when another job is already running for the project. The continuation job inherits the source job's `kind`, `sessionId`, and `provider`, sets `parentJobId` to the source job id, and runs with `base_prompt` plus a resume prompt that records the source job identity, original task when available, and a `RESUME_LOST_CONTEXT` escape hatch for evicted provider sessions. Because session IDs are provider-specific, the source provider is treated as strict: disabled or over-budget source providers block the continuation instead of falling back to another CLI.
- `/api/jobs/[jobId]/replay-actions` — Re-run the server-side agent action orchestrator for a completed agent job (POST). Reads the job log, extracts a fenced `tamtam-actions` block, checks action eligibility, dispatches idempotent issue/branch actions, and records `contextMeta.agentActions` counts. Returns `404` when the job or project is missing, `400` when no log path exists, `409` when the job is still running or actions are ineligible, `200 { replayed: false, reason, detail? }` when no executable action block is present, or `200 { replayed: true, executed, errors }` after dispatch.
- `/api/jobs/[jobId]/seen` — Mark job as seen (POST)
- `/api/jobs/notifications/mark-seen` — Mark all notifications seen (POST → `{ status: 'ok', marked }`, where `marked` is the number of finished unseen jobs flipped in the in-memory jobs cache)
- `/api/streaming/[jobId]` — SSE stream of parsed text deltas from NDJSON log (`?raw=1` for raw lines, `?passthrough=1` for mixed raw plus parsed logs). Nonzero synthetic `done` events may include `detail` only for failures without replayable raw/plain-text output; passthrough/plain-text failure lines are streamed as terminal output and are not duplicated in `detail`.

## Health / Monitoring / Stats

- `/api/health` — Health check (GET). Without query params this remains the lightweight public probe and returns `200 { status: 'ok' }`. `GET /api/health?deep=1` runs readiness checks and returns `{ status: 'ok'|'degraded', ok, checks: [{ name, ok, severity: 'info'|'warn'|'error', message }] }`; HTTP status is `503` only when an `error` severity dependency fails. Checks cover Postgres query, PM2, enabled provider launchers, scheduler connection state, workspace/project paths, `gh auth status` when auto-push projects can need PR workflow, and quota fetchability when budget gating is enabled.
- `/api/sweep` — Trigger the project sweep runner on demand (POST). Returns the `runProjectSweep()` report on success or `500 { error }` when the sweep throws.
- `/api/monitoring` — Prometheus + Loki status aggregation plus notification throttle state and separate retention telemetry for the latest nightly row cleanup and per-project log pruning summaries (GET); env: `PROMETHEUS_URL`, `LOKI_URL`
- `/api/monitoring/pm2-logs` — Tail tamtam PM2 log files (error + out from `~/.pm2/logs/`), last 64 KB; `?limit=` (max 500), `?out=0` to suppress stdout (GET)
- `/api/stats/usage` — Token usage per project, per agent kind, and per skill (GET, `?window=24h|7d|30d|all`). The `skills` breakdown is derived from `jobs.skill_ids`: prompt and cache-read tokens are split across a run's skills in proportion to each recorded skill prompt length, and `costUsd` covers those attributed prompt/cache-read tokens only.
- `/api/stats/ollama` — Local embedding telemetry aggregated from `ollama_usage`: totals plus per-model, per-source, and per-project breakdowns (GET, `?window=24h|7d|30d|all`; 60s cache)
- `/api/stats/pipeline` — Pipeline health metrics: verdict distribution, recovery-loop stats (`fix` jobs, attributed by `releaseId` when present and otherwise by the enclosing release window), step durations for the synthetic trigger `agent` step plus `release`, `test`, `review`, `fix`, `commit`, `push`, `pr-wait`, and `mark-dod` (each with `avg`, `median`, `p95`, `count`, and optional `avgCostUsd` when cost data exists), successful-release duration stats (`mttr.avg`, `mttr.median`, `mttr.p95`, `mttr.count`, optional `mttr.avgCostUsd`), per-project breakdown, and active recovery-budget config snapshot (`maxStepIterations`, `maxPushFixAttempts`, `stepWindowSeconds`; `maxStepIterations` is `null` when `fix_max_iterations = 0`, sourced from the same helper as runtime enforcement) (GET, `?window=...`, `?project=`; 60s cache)
- `/api/stats/system` — Live and recent host resource samples for the Stats bridge card (GET, optional `?limit=`, default 180, clamped to 1..1440). Returns `{ current, samples }`, where `current` is the newest CPU/memory/load/disk sample or `null`, and `samples` is the newest in-memory ring buffer slice.
- `/api/stats/bridge` — Fleet rollup for the `/stats` bridge card (GET; 15s cache). Returns `{ generatedAt, globalPace, throttle, projects, summary }`, where `globalPace` matches `/api/usage/quota` pace math, `throttle` is the multi-provider scheduled-agent burn-rate block verdict or `null`, and `projects[]` contains one row per project with at least one enabled non-system agent: `{ project, agents, status, paused, releaseRunning, lastPushAt, lastPushOk, lastReleaseAt, lastReleaseOk, lastAgentAt }`. Status precedence is `releasing`, `paused`, `attention`, `shipping`, `active`, then `idle`; `summary` rolls up project, agent, status, and running-release counts.
- `/api/stats/usage-history` — Hourly per-provider token usage and pace metrics for the 48-hour (or custom N-hour) usage chart on the stats page (GET; dynamic, no cache). Query parameter `hours` specifies the lookback window (default `48`, clamped to [1, 336]). Returns `{ generatedAt, hours, series }`, where each element in `series` represents one (provider, windowKey) pair and includes `{ provider, windowKey, buckets, currentTokensPerHour, expectedTokensPerHour, catchUpTokensPerHour }`. Each bucket in `buckets` contains `{ bucketTs, provider, windowKey, utilizationPct, elapsedPct, projectedPct, paceMarginPct, status, inputTokens, outputTokens, cacheReadTokens, cacheCreateTokens, jobCount, totalTokens }`, where `totalTokens` is the sum of input+output+cache read+cache create tokens scaled to tokens/hour (accounting for 15-minute bucket granularity). The three per-hour rates (`currentTokensPerHour`, `expectedTokensPerHour`, `catchUpTokensPerHour`) are scalars rendered as horizontal reference lines on the UI chart: `current` is the recent average spend, `expected` is the steady-state rate to reach 100% utilization by window end, and `catchUp` is the to-100% rate capped at 5× steady pace for chart readability. Data is sourced from `usage_hourly_snapshot`, populated by the background `usage-snapshot` cron task every 5 minutes. Returns `500 { error }` on database errors.
- `/api/stats/orchestrator` — Orchestrator and initiative-engine observability snapshot sourced entirely from durable DB data (GET; no cache). Returns `OrchestratorStatsResponse` (exported from the route): `{ generatedAt, flags, initiatives, actions }`. `flags` mirrors the four settings keys `orchestrator_enabled`, `initiative_engine_enabled`, `initiative_mining_enabled`, and `initiative_max_ships_per_day`. `initiatives.counts` is a `Record<InitiativeStatus, number>` with every status key present (zero-defaulted); `initiatives.shippedToday` is the count of `status='shipped'` rows whose `updatedAt >= start-of-UTC-day`; `initiatives.recent` is the 15 most-recently-updated rows mapped to `{ project, kind, status, source, score, updatedAt }`. `actions` covers the three orchestrator-origin recommendation types (`orchestrator_boost`, `agent_autopilot`, `orchestrator_agent_health`): `actions.last24h` counts each type with `updated_at >= now - 24h` (recommendations table stores `updated_at` in epoch-seconds); `actions.recent` is the 15 most-recent such rows mapped to `{ project, type, title, status, agentName, updatedAt }`. Returns `500 { error }` on database errors.
- `/api/initiatives` — All initiatives across all projects (GET). Returns `InitiativesListResponse` (exported from the route): `{ generatedAt, flags, counts, initiatives }`. `flags` reflects the four settings keys `initiative_engine_enabled`, `initiative_mining_enabled`, `initiative_max_ships_per_day`, and `initiative_max_backlog_per_project`. `counts` is a `Record<InitiativeStatus, number>` with every status key present (zero-defaulted). `initiatives` is the 200 most-recently-updated rows mapped to a slim shape `{ id, project, source, kind, title, rationale, score, status, releaseId, pinnedAt, updatedAt }` (omits `prompt`, `attempts`, `cooldownUntil`, `dedupKey`, `createdAt`). `pinnedAt` (epoch-ms or null) marks operator-promoted rows. Returns `500 { error }` on database errors.
- `/api/initiatives/[id]` — Operator steering for one mined initiative (PATCH). Body `{ action }`: `promote` pins a `proposed`/`queued` item to lead its project's queue (sets `pinned_at`; pinned-first in `listQueued` and the dispatcher); `unpromote` clears that pin; `reject` moves a `proposed`/`queued` item to `rejected` (the Miner will not reopen it); `restore` returns a `rejected` item to `queued`, clears any pin, and clears stale release/cooldown association fields. Curation is independent of the global `initiative_dispatch_enabled` gate — it orders what *would* ship once dispatch is on. In-flight and terminal rows (`running`, `shipped`, `failed`, `superseded`) are immutable through this endpoint so operator steering cannot hide active release tracking or requeue shipped work. Returns `200 { ok: true }`; `400 { error }` on invalid id or unknown action; `404 { error }` when the id is unknown; `409 { error }` when the action is not valid for the row's status; `500 { error }` on database errors.
- `/api/usage/quota` — Active provider quota snapshot (`?provider=claude|codex` overrides). GET/POST return `QuotaSnapshot & { available: true, gateEnabled: boolean, schedulerThrottle: null | { reason: string, projectedPct: number, worstProvider: 'claude'|'codex', resumesAtMs: number | null }, pace: { fiveHour, sevenDay }, globalPace }` on success. `pace` carries the selected provider's 5-hour and 7-day `WindowPace` values, while `globalPace` is the cross-provider binding pace. If a refresh fails after a successful fetch, the same shape is returned with `stale: true`, using the in-memory cache first and the last persisted `quota_snapshot:<provider>` value after a restart or upstream rate limit. Expected cold/unavailable states return `200 { available: false, configured: boolean, provider?, reason: 'not_configured'|'rate_limited'|'unavailable', error, gateEnabled, schedulerThrottle, globalPace }` so polling UI can render "quota unavailable" without surfacing backend 502 noise. `schedulerThrottle` is the server-computed multi-provider scheduled-agent weekly-throttle verdict: it is non-null only when every enabled provider that can actually run scheduled work is blocked on the 7d burn cap. Providers without quota fetchers (`gemini`, `lmstudio`) count as available fallback and keep `schedulerThrottle` null; quota-aware providers (`claude`, `codex`) count as unavailable only when their snapshot is missing while a sibling quota-aware provider has known quota data. POST force-clears cache and re-fetches all enabled quota-aware providers before computing that verdict.
